# qimo2 全面测试报告
> 测试时间: 2026-05-31
> 测试范围: 后端全部代码 + 前端全部页面 + 数据库 + 实际运行验证

## 一、致命级BUG（系统核心功能不可用）

### BUG-1: 云盘隔离失败 —— 新建云盘和旧云盘内容完全一致

**现象**: 创建第二个云盘(yun2)后，它和第一个云盘(yun1)显示的文件完全一样。

**根因**: 两个任务的 `remote_path` 都是 `/`，而 FTP 服务器只有一个根目录 `ftp_storage/`。
```
任务28(yun1): remote_path = '/' → 实际指向 ftp_storage/
任务35(yun2): remote_path = '/' → 实际指向 ftp_storage/
```
两个"云盘"读写的是同一个目录，所以内容必然一致。

**数据库证据**:
```
sync_tasks id=28: remote_path='/', ftp_server_id=14
sync_tasks id=35: remote_path='/', ftp_server_id=15
```
但两个 FTP 服务器(14和15)的 host:port 都是 `127.0.0.1:2121`，指向同一个 FTP 实例的同一个根目录。

**修复方向**: 创建 FTP 服务器时应自动分配隔离目录，如 `/user1/yun1`、`/user1/yun2`，并在 FTP 端确保目录隔离。

---

### BUG-2: 同步死循环 —— 同一文件被反复上传

**现象**: 数据库有 303 条同步历史记录，其中 147 条都是同一个文件 `新建 DOCX 文档.docx`，每 5 秒上传一次。

**根因**: 
1. FTP 服务器(pyftpdlib)不支持 MDTM 命令，返回 `mtime: None`
2. `NewestStrategy.should_sync()` 在 mtime 为 None 时回退到 size 比较
3. 上传文件后，本地文件的 mtime 更新了（因为 read 操作），但 size 没变
4. 下次定时扫描(10秒间隔)时，本地 mtime 变了 → 触发 should_sync → 重新上传
5. 无限循环

**关键代码** (`sync_engine.py` 第 36-54 行):
```python
def should_sync(self, local_info, remote_info):
    if local_info.get('mtime') is None or remote_info.get('mtime') is None:
        return local_info.get('size') != remote_info.get('size')  # 回退到 size
    return local_info['mtime'] != remote_info['mtime']

def get_direction(self, local_info, remote_info):
    if local_info.get('mtime') is None or remote_info.get('mtime') is None:
        return 'local_to_remote'  # 永远上传！
```
问题: 当 mtime 不可用时，`get_direction` 永远返回 `local_to_remote`，即使文件已经一致。

**修复方向**: 
- 记录上次同步的文件 hash/size，避免重复同步
- 或者在 FTP 端支持 MDTM 命令
- 或者用"本地记录上次同步状态"的方式判断

---

### BUG-3: 本地修改后云端不同步

**现象**: 你在本地改了一个文件，云端不会自动更新。

**根因**: WSL 下对 `/mnt/c/` (Windows 挂载) 的 inotify 监控不可靠。watchdog 的 `Observer` 无法可靠检测到 Windows 侧的文件变化。

**代码中的处理** (`sync_routes.py` 第 164-167 行):
```python
# WSL下Windows挂载路径（/mnt/c/...）的inotify不可靠，自动缩短扫描间隔
if get_is_wsl() and local_path.startswith('/mnt/'):
    if scan_interval > 15:
        scan_interval = 10
```
虽然缩短了扫描间隔到 10 秒，但定时扫描触发的是全量同步，而全量同步又因为 BUG-2 的死循环问题，导致每次都重复上传相同的文件，真正的修改反而被淹没了。

**修复方向**: 
- 定时扫描时先比对本地和远端的文件 hash，只有真正变化的才同步
- 修复死循环问题后，定时扫描才能正确检测到变化

## 二、严重级BUG（功能异常）

### BUG-4: `sync_test.txt` 等莫名其妙的文件

**现象**: FTP 根目录下有 `sync_test.txt`、`新建 DOC 文档.doc` 等用户没创建的文件。

**根因**: 这些是之前测试遗留的文件。因为所有任务的 `remote_path` 都指向同一个 `/` 目录，旧任务遗留的文件会出现在所有新"云盘"中。

**验证**: 
```
ftp_storage/ 目录内容:
  auto_test/          ← 测试遗留
  sync_test.txt       ← 测试遗留
  新建 DOC 文档.doc   ← 测试遗留
  新建 DOCX 文档.docx ← 同步死循环反复上传的
```

---

### BUG-5: Office 临时文件(~$)未被正确忽略

**现象**: `~$ DOCX 文档.docx` 出现在 yun2 本地目录中，但没有被同步到云端（这部分是对的），可是 watcher 仍然检测到了这个文件并触发了同步事件。

**根因**: `watcher.py` 的 `_should_ignore_event()` 方法:
```python
IGNORED_PREFIXES = ('.', '~')
def _should_ignore_event(self, path):
    name = os.path.basename(path)
    if name.startswith(self.IGNORED_PREFIXES):  # '~$ DOCX...' 以 '~' 开头？
        return True
```
`~$ DOCX 文档.docx` 以 `~` 开头，所以会被 watcher 忽略。但问题是 `sync_engine.py` 的全局忽略规则 `~$*` 用的是 fnmatch 匹配:
```python
DEFAULT_IGNORE_PATTERNS = ['~$*', ...]
```
`~$*` 匹配 `~$ DOCX 文档.docx` 吗？**不匹配！** 因为 `~$*` 要求 `$` 后面直接是任意字符，但文件名是 `~$ DOCX...`（$后面有空格）。fnmatch 的 `*` 匹配任意字符，所以 `~$*` 实际上应该匹配。但让我验证一下...

实际上 `~$*` 是能匹配 `~$ DOCX 文档.docx` 的，因为 `*` 匹配 ` DOCX 文档.docx`。所以同步引擎会忽略它。但 watcher 层面因为文件名以 `~` 开头也会忽略。所以这个文件不会被同步，但会被 watcher 检测到并打印日志。

**结论**: 这个文件不会被同步（正确），但 watcher 日志中会出现它的检测记录（噪音）。用户说的"打开文档会产生这个"是正常的 Office 行为，系统处理是正确的。

---

### BUG-6: `newest` 策略在 mtime 不可用时形同虚设

**根因**: pyftpdlib 默认不支持 MDTM 命令，`scan_remote()` 返回的 `mtime` 始终为 `None`。

**影响**: 
- `should_sync()` 回退到 size 比较
- `get_direction()` 永远返回 `local_to_remote`
- 云端修改的文件永远不会同步到本地
- "以最新文件为准"这个策略完全失效

---

### BUG-7: `size` 策略永远上传本地

**根因** (`sync_engine.py` 第 65-72 行):
```python
class SizeStrategy(SyncStrategy):
    def get_direction(self, local_info, remote_info):
        if local_info['size'] != remote_info['size']:
            return 'local_to_remote'  # 永远是本地→远端！
        return 'skip'
```
当 size 不同时，永远选择上传本地，而不是比较谁更新。这在"远端修改了文件"的场景下会覆盖远端的修改。

## 三、中等级BUG（体验问题）

### BUG-8: 删除同步只在强制方向策略下生效

**代码** (`sync_engine.py` 第 331 行):
```python
if task.delete_sync and task.force_direction in ('local', 'remote'):
```
使用 `newest` 或 `size` 策略时，即使开启了 `delete_sync`，删除也不会传播。

---

### BUG-9: 连接池复用可能导致跨任务串扰

**代码** (`ftp_routes.py` 第 30 行):
```python
key = f"{server_config['host']}:{server_config['port']}"
```
连接池以 host:port 为 key，如果两个 FTP 服务器配置指向同一个地址，会复用同一个连接，但连接的 cwd 状态可能被前一个任务改变。

---

### BUG-10: 数据库连接未使用上下文管理器

多处代码用 `conn = get_db()` 后手动 `conn.close()`，如果中间抛异常会导致连接泄漏。应该用 `with` 语句。

## 四、UI/UX 问题

### UX-1: 没有文件上传功能
Files 页面只能浏览和"拉取"远端文件，不能上传文件到本地或远端目录。用户无法通过 Web 界面管理文件。

### UX-2: 没有文件/文件夹创建功能
无法在 Web 界面创建新文件夹或上传新文件。

### UX-3: 没有文件删除功能
无法通过 Web 界面删除文件。

### UX-4: 没有文件搜索功能
文件多了以后无法快速定位。

### UX-5: 差异对比只比较根目录一层
`files_routes.py` 的 diff 功能只扫描根目录一层文件，不递归，子目录中的差异看不到。

### UX-6: 历史记录太多太杂
303 条记录，147 条是同一个文件的重复上传。没有清理机制，没有按任务筛选（虽然有 API 但前端没用）。

### UX-7: Dashboard 统计数据不准
成功/失败统计被死循环的重复记录污染，数据没有参考价值。

### UX-8: 界面设计比较朴素
- 登录页还行，但整体配色和现代云盘(如百度网盘、坚果云)差距较大
- 没有文件图标系统(不同文件类型用不同图标)
- 没有缩略图预览
- 没有深色模式
- 没有响应式设计(移动端不可用)

### UX-9: 创建任务时 remote_path 默认是 /
用户如果不改，所有任务都会指向同一个 FTP 根目录，导致隔离失败。应该自动根据任务名生成隔离路径。

### UX-10: 没有批量操作
不能批量删除文件、批量同步、批量暂停任务。

### UX-11: 没有实时进度反馈
手动同步时只有 loading 状态，没有进度条或逐文件的实时反馈。

### UX-12: 文件大小显示在目录切换后不更新
切换目录后文件列表重新加载，但差异对比状态(diffMap)不自动更新。

## 七、修复建议（按优先级）

### 必须修复（否则项目演示会出大问题）

1. **云盘隔离**: 创建 FTP 服务器时自动生成隔离的 remote_path，如 `/{username}/{server_name}/`，确保不同云盘读写不同目录

2. **修复同步死循环**: 
   - 本地维护"上次同步状态表"(文件路径 + hash/size + 同步时间)
   - 只有状态变化的文件才同步
   - 或者同步完成后记录快照，下次比对快照

3. **修复 newest 策略**: 
   - 方案A: 让 pyftpdlib 支持 MDTM（需要修改 FTP 服务器配置）
   - 方案B: 同步引擎在本地记录远端文件的"上次已知 mtime"
   - 方案C: 用文件 hash 代替 mtime 做比较

4. **修复本地监控**: WSL 下 inotify 不可靠是已知问题，当前的定时扫描方案可以作为兜底，但需要先修复死循环

### 建议修复（提升演示效果）

5. 添加文件上传功能
6. 添加文件/文件夹创建功能
7. 优化历史记录展示（去重、分页、按任务筛选）
8. 美化界面（更好的配色、文件图标、进度条）
